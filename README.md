# MpiPlatform

Десктопное приложение (Qt6/C++17) для стенда диагностики трубопроводной арматуры — управляет испытательным оборудованием через модуль **МПИ** (последовательный порт), проводит серию тестов позиционера/привода и формирует итоговый отчёт (Excel, PDF, CSV).

Раньше это были три независимых репозитория, разошедшихся под разных заказчиков. Сейчас это одна кодовая база, которая тремя разными сборками закрывает все три сценария. Этот README объясняет, как это устроено и почему именно так.

## Три варианта сборки

Приложение собирается в один исполняемый файл, но с одним из трёх наборов поведения — выбирается флагом CMake на этапе конфигурации, а не отдельной веткой/форком в git.

| Вариант | Для чего |
|---|---|
| **Standard** | Базовая версия без заказных доработок — то, что подходит большинству заказчиков "из коробки". |
| **Ilim** | Вариант под конкретное производство: своя логика привода двойного действия (ДД), отдельные листы отчёта (ТЧР/ТРС), возможность выбора цвета кривых/датчиков в интерфейсе. Специфика этого заказчика раньше жила в отдельном форке — теперь это просто явная развилка внутри общего кода. |
| **Ski** | Вариант с поддержкой циклических испытаний запорно-регулирующей арматуры: работа с дискретными входами/выходами (DO/DI), соленоидные клапаны, пять программ тестирования (полные/базовые испытания регулирующей и запорно-регулирующей арматуры), отдельный лист отчёта "ЦТ". |

Почему не три отдельных репозитория, как было раньше: три версии — это один и тот же прибор с одним и тем же протоколом обмена и почти одинаковым интерфейсом, у которых разошлась примерно десятая часть кода. Три репозитория означали, что общий баг (а их находилось немало — см. ниже) приходилось чинить трижды, и рано или поздно чинили не везде одинаково. Один код с явно размеченными развилками решает это по построению.

### Как это устроено технически

- `Src/Domain/BuildVariant.h` — единственное место с `#ifdef` во всём проекте:
  ```cpp
  enum class Variant { Standard, Ilim, Ski };
  inline constexpr Variant kVariant = /* из MPISDK_VARIANT_ILIM / MPISDK_VARIANT_SKI */;
  inline constexpr bool kIlimVariant = (kVariant == Variant::Ilim);
  inline constexpr bool kSkiVariant  = (kVariant == Variant::Ski);
  ```
- Везде остальные — `if constexpr (Domain::kIlimVariant)` / `if constexpr (Domain::kSkiVariant)`, никогда не `#ifdef`. Это осознанный выбор: обе ветки всегда компилируются и проверяются типами, компилятор просто выбрасывает недостижимую. Скрытый за `#ifdef` код в этом проекте не раз незаметно ломался — в нём накапливались настоящие баги, которые всплывали только когда кто-то наконец собирал ту сборку.
- Вариант выбирается флагом CMake:
  ```bash
  cmake -B build -DMPISDK_VARIANT=Ski    # или Standard / Ilim
  cmake --build build
  ```
  Флаг превращается в `target_compile_definitions(Domain PUBLIC MPISDK_VARIANT_SKI)` на уровне библиотеки `Domain`, а дальше распространяется на `Report` и `Gui` (обе линкуют `Domain` как `PUBLIC`), так что во всех трёх слоях видно одно и то же значение.

Расхождения между вариантами по факту небольшие и локальные: видимость вкладок и кнопок в интерфейсе, доступность DO/DI, набор листов и раскладка отчёта, пара мест в логике привода. Общий код (протокол обмена с устройством, ядро тестов, генерация базовых отчётов) — один на все три.

## Что делает приложение

- Подключается к устройству (МПИ) по COM-порту, инициализирует его, читает телеметрию (положение, давление, дискретные входы/выходы).
- Проводит тесты: ручное управление, тест полного хода, основные тесты (позиционер), опциональные тесты (шаговая реакция, отклик/разрешение — Ilim), циклические тесты (Ski).
- Строит графики по ходу теста (задание/датчики/давление).
- Формирует итоговый отчёт — Excel-документ по шаблону конкретного варианта/паттерна, плюс PDF-акты и CSV-выгрузки графиков.

### Генерация отчёта — тоже развилка, но другая

Отчёт собирается тремя независимыми путями из одних и тех же данных:

- **Excel** (`Src/Report/Excel`) — построчная запись в шаблон `.xlsx` через QXlsx (вендоренная библиотека, `QXlsx/`). Шаблон свой для каждого варианта/паттерна (`Reports/*.xlsx`).
- **PDF** (`Src/Report/Pdf`) — через QtRPT (вендоренный движок отчётов, `QtRPT/`), свои XML-шаблоны полос.
- **CSV** (`Src/Report/Csv`) — прямая выгрузка данных графика.

Все три получают на вход один и тот же `Report::Context` (объект/клапан/телеметрия/графики/паттерн) — это специально сделано так, чтобы Excel/PDF/CSV не могли разойтись по данным между собой, только по форме.

## Структура репозитория

```
Src/
  Domain/     — логика тестов, работа с устройством (UART), сценарии/анализаторы, домен без UI
  Report/     — генерация отчётов (Excel/Pdf/Csv), общий Report::Context
  Gui/        — окна, презентеры (MainWindow и его расшивка на Presenter-классы)
  Widgets/    — графики, слайдеры, тосты — переиспользуемые виджеты
  Storage/    — реестр настроек объекта/клапана/телеметрии, персистентность
QXlsx/        — вендоренная библиотека чтения/записи .xlsx (не наша, не патчим)
QtRPT/        — вендоренный движок PDF-отчётов (не наша, не патчим)
Reports/      — шаблоны .xlsx отчётов, по одному на вариант/паттерн
tests/        — модульные тесты (напр. AnalyzerTests)
experiments/  — одноразовые диагностические стенды (verify-report, verify-theme, ...) —
                не часть приложения, используются только при рефакторинге для сверки
                "до/после", безопасно удаляются по отдельности
```

Три библиотеки (`Domain` → `Report` → `Gui`, именно в таком порядке зависимостей) и один исполняемый файл (`MpiSdk`) — собираются из `Src/CMakeLists.txt` и корневого `CMakeLists.txt` соответственно.

## Сборка

Требования: Qt 6.8+, CMake 3.21+, компилятор с поддержкой C++17.

```bash
cmake -B build -DMPISDK_VARIANT=Standard   # Standard | Ilim | Ski
cmake --build build
```

Дополнительные CMake-опции (все по умолчанию выключены) собирают вспомогательные цели из `experiments/` и `tests/` — см. соответствующие `option(...)` в корневом `CMakeLists.txt`.

## О названии

Имя `MpiPlatform` — для самого репозитория/кодовой базы, не для продукта: `Mpi` — по названию аппаратного модуля, с которым работает софт; `Platform` — потому что отсюда собираются три разных продуктовых варианта, а не один. Сам исполняемый файл по-прежнему называется `MpiSdk` — это осознанно оставлено как есть.

Один из трёх вариантов называется `Ski` — это тоже не случайное имя, а название конкретного продукта. С аббревиатурой `Sdk` (в имени бинарника/старых репозиториев) её не стоит путать: несмотря на похожее звучание, это два независимых имени о разных вещах — `Sdk` тут не имеет отношения к "software development kit", это тоже часть исторического названия комплекса, а не аббревиатура на английском.
